## 1. Using Git in CI/CD Pipelines

### A. What is CI/CD?

**Continuous Integration (CI)** – Automates testing when new code is pushed.\
**Continuous Deployment (CD)** – Automatically deploys code to production after passing tests.

✅ **Goal:** Every change is **built, tested, and deployed** automatically.

Popular CI/CD tools:

* **GitHub Actions** (`.github/workflows/`)
* **GitLab CI/CD** (`.gitlab-ci.yml`)
* **Jenkins, CircleCI, Travis CI**

***

### B. Triggering CI/CD on Git Events

Git enables **automation** by triggering CI/CD workflows based on events like:

* **`push` to `main`** → Run tests and deploy
* **Pull Request (`PR`) created** → Run static analysis
* **Tag a commit** → Deploy a release

Example GitHub Actions workflow (`.github/workflows/main.yml`):

```yaml
name: CI Pipeline
on: push
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Install dependencies
        run: npm install
      - name: Run tests
        run: npm test
```

✅ **Use case:** Automatically run tests when pushing new code.

***

### C. Enforcing Branch Protection in CI/CD

Large teams prevent mistakes by **protecting branches** using Git and CI/CD:

1️⃣ **Require PR approvals before merging**\
2️⃣ **Prevent force pushes on `main`**\
3️⃣ **Require CI checks to pass before merging**

Example GitHub branch protection settings:

- ✅ ✅ Require PR reviews
- ✅ ✅ Require status checks (tests, linting)
- ✅ ✅ Restrict direct pushes to `main`

## 2. Managing Large Git Repositories

Git works well for small projects, but **large monorepos** can slow down over time.

### A. Best Practices for Scaling Git Repos

✅ **Use shallow clones** for speed:

```sh
git clone --depth=1 https://github.com/user/repo.git
```

✅ **Enable sparse checkout** to only fetch necessary files:

```sh
git sparse-checkout init
git sparse-checkout set src/
```

✅ **Use Git LFS (Large File Storage)** for binaries and media files:

```sh
git lfs install
git lfs track "*.png"
```

✅ **Archive old branches** and delete stale ones:

```sh
git branch -d old-branch
```

✅ **Avoid committing large files**—store them in S3, Artifactory, or Nexus instead.

🚀 **Use case:** Keeping repositories fast and lightweight as they grow.

## 3. Security Best Practices in Git

### A. Signing Commits for Verification

Ensure commits come from trusted sources using **GPG keys**:

```sh
git config --global user.signingkey YOUR-GPG-KEY-ID
git commit -S -m "Signed commit"
```

✅ Protects against **supply chain attacks** and unauthorized changes.

***

### B. Preventing Secrets in Git

**Accidentally pushing API keys is a major security risk!**

✅ Use **`.gitignore`** to prevent committing secrets:

```sh
echo ".env" >> .gitignore
```

✅ Scan for secrets using:

```sh
git-secrets --scan
```

✅ Remove a secret from Git history (after pushing):

```sh
git filter-branch --force --index-filter \
  "git rm --cached --ignore-unmatch path/to/secret-file"
```

✅ Use **environment variables** instead of storing secrets in Git.

🚀 **Use case:** Preventing security leaks in repositories.

## 4. GitOps – Infrastructure as Code

### A. What is GitOps?

GitOps is the practice of using **Git as the single source of truth** for infrastructure and deployments.

- ✅ **All infrastructure changes are stored in Git**
- ✅ **Kubernetes deployments are automated** using Git
- ✅ **Rollback infrastructure easily using Git history**

Popular GitOps tools:

* **ArgoCD**
* **FluxCD**

### B. Example GitOps Workflow

1️⃣ Devs push changes to a **Git repository**\
2️⃣ CI/CD pipeline validates the infrastructure code\
3️⃣ GitOps tool **automatically applies changes** to Kubernetes

Example **ArgoCD** GitOps process:

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
spec:
  source:
    repoURL: https://github.com/my-org/k8s-configs.git
    path: apps/my-app
    targetRevision: main
```

🚀 **Use case:** Automating Kubernetes deployments via Git commits.
